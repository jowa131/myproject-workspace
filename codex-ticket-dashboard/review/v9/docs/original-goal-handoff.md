# Codex 작업 티켓 대시보드 원래 목적·목표 편차·교정 인계서

- 문서 상태: `CORRECTION-HANDOFF-ACTIVE`
- 작성일: 2026-09-07 KST
- 대상 프로젝트: `C:\MyProject\codex-ticket-dashboard`
- 상위 Git 저장소: `C:\MyProject`
- 현재 제품 수준 판정: `FOUNDATION-COMPLETE / AUTO-PROJECTION-INCOMPLETE / PRODUCT-GOAL-INCOMPLETE`
- 용도: 다른 모델이 과거의 좁은 완료 판정을 제품 완료로 오인하지 않고, 원래 목적을 복원한 교정 계획을 작성하기 위한 인계 원본

## 1. 결론

현재 산출물은 사건 기록·spool·수집기·SQLite·읽기 전용 웹을 갖춘 검증된 기반입니다. 그러나 Codex 작업 생명주기와 기록 도구를 자동으로 연결하는 관찰 계층이 없으므로, 사용자가 기대한 자동 작업 추적 제품은 완성되지 않았습니다.

과거의 `MCP-FIRST-DESKTOP-CANDIDATE-USER-ACCEPTED / DESKTOP-SCOPE-COMPLETED`는 좁은 후보 산출물에 대한 역사적 수락 상태로만 보존해야 합니다. 이 상태를 원래 제품 목적 달성이나 자동 투영 완료의 근거로 사용해서는 안 됩니다.

## 2. 원래 제품 목적

이 프로젝트의 원래 목적은 다음과 같습니다.

> 여러 Codex Desktop·CLI 작업을 사용자가 별도로 등록하거나 정리하지 않아도, 작업 시작·진행·차단·검토·사용자 수락 상태를 자동으로 구조화하여 프로젝트와 티켓 단위로 보여주는 로컬 읽기 전용 관찰 대시보드를 만든다.

사용자가 대시보드에서 확인할 수 있어야 하는 핵심 정보는 다음과 같습니다.

- 어떤 Codex 작업이 새로 시작됐는지
- 작업이 어느 프로젝트와 티켓에 연결됐는지
- Task·Subtask가 어떤 상태인지
- 현재 진행 중인지, 사용자 답변 대기인지, 차단됐는지
- Codex가 결과를 제출해 `IN_REVIEW`인지
- 사용자가 명시적으로 수락해 `COMPLETED`인지
- Git·Wiki·검증 게이트가 충족됐는지
- 차단 사유와 다음 단계가 무엇인지
- 기록 누락 또는 수집 장애가 발생했는지

제품의 기본 흐름은 다음과 같습니다.

```text
Codex Desktop·CLI 작업
  -> 생명주기 사건 자동 관찰
  -> 구조화 기록
  -> 원자 spool
  -> 단일 수집기
  -> SQLite WAL 투영·이력
  -> 로컬 읽기 전용 웹 대시보드
```

웹은 Codex, Git, Wiki 또는 티켓을 제어하거나 수정하지 않습니다. 웹에서 Codex로 향하는 역제어 경로는 허용하지 않습니다.

## 3. 원래 성공 기준

승인 설계서가 명시한 최상위 성공 기준은 다음과 같습니다.

1. 새 Codex 스레드가 별도 사용자 입력 없이 수집 기록으로 생성됩니다.
2. 명확한 작업은 신규 또는 기존 티켓에 연결되고 Task·Subtask를 가질 수 있습니다.
3. 사용자 피드백과 Codex 결과가 동일한 turn 관계로 연결됩니다.
4. 분류에 실패한 활동도 사라지지 않고 `UNCLASSIFIED`로 표시됩니다.
5. 결과 보고 시 작업 상태, Git 게이트, Wiki 게이트, 검증 결과와 다음 단계가 함께 갱신됩니다.
6. 수집기가 중단되어도 spool 사건은 재시작 뒤 중복 없이 반영됩니다.
7. 웹에는 Codex 제어 또는 티켓 변경 endpoint가 없습니다.
8. 대시보드 장애가 Codex 작업 자체를 막지 않으며, 기록 누락은 명시적으로 드러납니다.
9. 비밀값과 사용자 prompt·assistant message·transcript·Hook 출력의 원문 또는 발췌를 저장하지 않습니다.
10. Codex는 `IN_REVIEW`까지만 전환하며, 완료·취소·재개는 사용자의 명시적 결정만 허용합니다.

이 중 1번과 이를 지속시키는 생명주기 자동 연결은 제품 목적의 필수 조건입니다. 이를 제외한 상태를 제품 완료로 판정할 수 없습니다.

다음 기반은 구현되어 있으며 기존 검증 기록을 보존합니다.

## 5. 현재 빠진 핵심 기능

### 5.1 자동 호출 트리거 부재

현재 MCP 등록은 Codex에 기록 도구를 노출합니다. 그러나 다음 생명주기 사건과 대시보드 도구를 연결하는 활성 대시보드 Hook이 없습니다.

- `SessionStart`
- `UserPromptSubmit`
- `PreToolUse`
- `PostToolUse`
- `Stop`
- `SessionEnd`

따라서 기록 도구 호출은 정해진 자동 사건이 아니라 각 턴에서 모델이 사용자 지시, 작업 문맥과 도구 설명을 보고 선택하는 호출입니다. 신규 스레드 생성, 기존 스레드 재개, 사용자 메시지 전송, 작업 종료 또는 PC 재시작 자체는 현재 대시보드 기록 트리거가 아닙니다.

### 5.2 누락 검출·보정 부재

승인 설계서는 Stop 시점에 preflight·Task·summary·gate·status 기록을 검사하고 필요한 경우 한 차례 보정 continuation을 수행하도록 정의했습니다. 현재 수락 후보에는 이 Stop 검증 연결이 없습니다. 그러므로 모델이 기록 호출을 생략해도 자동으로 감지하거나 보정하지 못합니다.

### 5.3 실제 사용자 시나리오 검증 부재

기존 시험은 MCP 호출 이후의 spool·수집·DB·웹 흐름을 충분히 검증했지만, 다음 최상위 시나리오를 완료 조건으로 실행하지 않았습니다.

> 새 Codex 작업을 만들고 대시보드 관련 추가 지시를 하지 않아도 해당 작업이 자동으로 생성·갱신·종료 상태까지 투영되는가?

이 시나리오가 빠진 상태에서 구성요소 시험 통과를 제품 완료로 보고했습니다.

### 5.4 재시작 의미의 제한

SQLite와 spool 데이터는 재시작 뒤 유지되고, 웹 수집기는 시작 시 대기 사건을 다시 읽습니다. 그러나 재시작 뒤 Codex가 기록 도구를 자동으로 호출하도록 만드는 연결은 없습니다. 따라서 데이터 지속성은 검증됐지만 자동 추적 지속성은 검증되지 않았습니다.

### 5.5 웹 자동 시작 부재

현재 웹·수집기 런타임은 수동 시작 방식입니다. 이는 자동 작업 관찰과 별개의 운영 문제지만, PC 재시작 뒤 사용 가능한 대시보드라는 사용자 경험을 완성하려면 명시적 운영 결정이 필요합니다. 자동 시작 주기·방식은 사용자의 별도 승인 없이 추가해서는 안 됩니다.

### 5.6 과거 스레드 백필

과거 전체 스레드 백필은 기존 작업 패킷에서 명시적으로 제외됐습니다. 이는 신규·재개 작업의 자동 관찰 누락과 구분해야 합니다. 교정 작업은 우선 향후 사건의 자동 투영을 복원하고, 과거 백필은 개인정보·비용·식별 위험을 별도 검토한 뒤 독립적으로 결정해야 합니다.

## 6. 문제가 발생한 경위

### 6.1 역사적 흐름

1. 승인 설계서는 Codex Hooks를 실시간 수집 경로로 두고 새 스레드의 무개입 수집을 성공 기준으로 정의했습니다.
2. Phase 0 v1.1은 `FAIL-BLOCKED`, 소유 잔여물 복구는 `OWNED-RESIDUE-CLEAN`, 비침습 재평가는 `LIMITED`로 남았습니다.
3. 이후 실행 범위를 `MCP-FIRST-DESKTOP-CANDIDATE`로 축소했습니다.
4. 2026-09-05 Phase 1 작업 패킷은 Hook·plugin·Codex config·App Server 변경과 재시험, 자동 실행, 과거 스레드 백필을 비목표로 명시했습니다.
5. 사건·DB·MCP·웹 기반을 구현하고 기존 manifest, 검토 승인과 99개 시험을 근거로 데스크톱 후보를 제시했습니다.
6. 2026-09-06 사용자는 제시된 후보 산출물을 명시적으로 수락했습니다.
7. 이후 이 수락을 `DESKTOP-SCOPE-COMPLETED`로 기록하면서, 원래 성공 기준 1번이 제외됐다는 사실을 제품 수준 미완료 상태로 함께 유지하지 못했습니다.
8. 2026-09-07 재시작과 기록 트리거를 재확인하는 과정에서 MCP 도구 노출과 자동 생명주기 호출이 서로 다른 기능이며, 현재 후보에는 후자가 없다는 점이 명확해졌습니다.

### 6.2 핵심 판단 오류

문제는 단순 구현 누락만이 아니라 목표와 완료 기준을 관리한 방식에 있습니다.

- 기술적 위험을 줄이기 위한 임시 실행 범위를 제품 목적의 대체 범위로 취급했습니다.
- 자동 투영을 `BLOCKED` 또는 `PARTIAL`로 유지하지 않고 작업 패킷의 비목표로 이동했습니다.
- 축소 범위가 원래 목적을 충족하지 못한다는 점을 사용자 승인 전에 충분히 명시하지 않았습니다.
- 구성요소 검증을 사용자 핵심 결과의 종단 간 검증으로 잘못 대체했습니다.
- 좁은 후보 수락과 제품 목적 수락을 상태 이름에서 명확히 분리하지 않았습니다.
- “새 실제 Codex 스레드가 아무 추가 지시 없이 나타나는가”를 최종 필수 수락 시험으로 두지 않았습니다.

사용자 승인은 기존 기반 후보 산출물에 대한 역사적 수락으로 존중해야 합니다. 그러나 원래 목적 미달 사실이 충분히 공개되지 않은 상태의 수락을 제품 목적 변경 승인이나 자동 추적 완료의 근거로 확대 해석해서는 안 됩니다.

## 7. 현재 영향

- 모든 신규 Codex 스레드가 대시보드에 나타난다고 보장할 수 없습니다.
- 기존 스레드의 새 활동도 기록 도구가 선택적으로 호출된 경우에만 추가됩니다.
- 모델이 도구를 호출하지 않으면 누락을 자동 검출하거나 보정하지 못합니다.
- 대시보드는 수동 호출 또는 선택적 모델 호출로 들어온 사건은 정상 처리하지만, 전체 Codex 작업의 신뢰 가능한 관찰 원본은 아닙니다.
- 현재 대시보드를 “사용자 무개입 자동 작업 추적 제품” 또는 “원래 목적에 맞게 완료된 제품”이라고 보고하면 안 됩니다.

## 8. 상태 교정 원칙

### 8.1 제품 수준 상태

현재 제품 수준 정본 판정은 다음과 같아야 합니다.

```text
FOUNDATION-COMPLETE
AUTO-PROJECTION-INCOMPLETE
PRODUCT-GOAL-INCOMPLETE
CORRECTION-PLAN-NOT-YET-APPROVED
```

### 8.2 역사 기록 보존

- 기존 Phase 0 판정과 증거 hash는 변경하지 않습니다.
- 기존 후보 manifest, 시험 통과와 검토 승인 결과를 폐기하거나 성공에서 실패로 다시 쓰지 않습니다.
- `MCP-FIRST-DESKTOP-CANDIDATE-USER-ACCEPTED`는 좁은 기반 후보에 대한 역사적 사실로 유지합니다.
- `DESKTOP-SCOPE-COMPLETED`는 제품 목적 완료가 아니라 해당 축소 범위의 종료 표식이었다고 명시합니다.
- 새로운 교정 기록은 과거 문서를 삭제하거나 소급 개작하지 않고 append-only 방식으로 우선순위를 갖게 해야 합니다.

### 8.3 완료 용어 사용 제한

향후 다음 조건을 실제로 관찰하기 전에는 `PRODUCT-COMPLETED`, `AUTO-PROJECTION-COMPLETED`, “사용 가능한 자동 추적 상태”라고 보고하지 않습니다.

> 신규 또는 재개 Codex 작업이 대시보드용 별도 사용자 지시 없이 자동으로 기록되고, 진행·차단·검토·사용자 결정 상태가 누락 검출과 함께 끝까지 투영된다.

## 9. 권장 교정 아키텍처

다음 방향은 교정 계획의 출발점이며, 구현 승인 전 별도 설계 검토가 필요합니다.

### 9.1 생명주기 관찰 계층 복원

- `UserPromptSubmit`: 원문을 저장하지 않고 thread·turn·프로젝트 source metadata를 기반으로 신규 활동을 관측합니다.
- 첫 실질 작업 전: 필요한 경우 `ticket_preflight_record`를 호출하고 신규 또는 기존 티켓 연결을 확정합니다.
- Task 변경 시: `task_upsert`로 Task·Subtask 생성과 상태 변화를 기록합니다.
- `PostToolUse`: 지원되는 변경 도구 실행 사실을 개인정보 안전 metadata로 관측하고, preflight 누락 또는 상태 편차를 표시합니다.
- 최종 응답 전: 적용되는 `git_gate_report`, `wiki_update_record`, `ticket_turn_summary`, `ticket_status_update`를 인과 관계와 함께 기록합니다.
- `Stop`: 필수 기록 집합을 검사하고 누락이 있으면 최대 한 차례 bounded continuation으로 보정합니다.
- `SessionEnd`: 완료 권한 근거로 사용하지 않고 종료 진단만 남깁니다.

### 9.2 MCP와 Hook의 역할 분리

- MCP 도구는 구조화 사건을 spool에 기록하는 권위 입력 경로를 유지합니다.
- Hook은 언제 기록 또는 검사가 필요한지를 결정하는 생명주기 연결 계층입니다.
- Hook 출력이나 사용자 원문을 저장하지 않습니다.
- Hook 실패가 Codex 본 작업을 손상시키지 않되, 기록 누락은 `UNCLASSIFIED` 또는 명시적 수집 문제로 드러나야 합니다.
- `SessionStart` 시 MCP 연결이 아직 준비되지 않을 수 있으므로 시작 사건의 안정적 전달 방식은 Phase 0에서 별도로 검증해야 합니다.

### 9.3 App Server의 제한적 위치

App Server는 실시간 기록의 주 경로로 간주하지 않습니다. 현재 Host에서 안전성과 공식 지원 경계를 다시 검증한 경우에만 누락 진단 또는 제한적 복구 후보로 사용합니다. 실제 transcript 전체 읽기나 과거 대화 무차별 백필은 허용하지 않습니다.

### 9.4 자동 시작은 별도 운영 결정

PC 재시작 후 웹·수집기를 자동 실행할지는 자동 투영 로직과 분리해 결정합니다. 예약 작업, 서비스, 시작 프로그램 또는 기타 반복·백그라운드 실행은 정확한 방식, 비용, 중지 조건, 중복 방지와 사용자 권한을 먼저 승인받아야 합니다.

## 10. 교정 실행 단계

### 단계 0. 권위 상태 교정

- 본 인계서를 검토합니다.

- 사용자 승인 전 기존 권위 문서를 임의로 수정하지 않습니다.

### 단계 1. 자동 관찰 작업 패킷 작성

새 작업 패킷에는 다음을 필수로 포함합니다.

- 목표: 실제 Codex 신규·재개 작업의 무개입 자동 투영
- 비목표: 과거 전체 transcript 백필, 웹 역제어, 원문 저장, 미승인 자동 시작
- Hook 사건별 입력·출력·개인정보 allowlist
- MCP 연결 준비 전·후 처리
- 누락·중복·역순·재시작 복구 계약
- Stop continuation 최대 횟수
- 기존 MCP-first 기반과의 호환성
- 실패 시 `BLOCKED`, `LIMITED`, `PARTIAL` 판정 기준
- 사용자 최종 수락 시나리오

### 단계 2. Phase 0 호환성 재검증

실제 현재 Codex Desktop·CLI와 Windows 환경에서 최소 다음을 확인합니다.

- 필요한 Hook 사건의 발화 여부
- thread·turn 식별자 안정성
- MCP tool hook 연결 준비 시점
- `UserPromptSubmit`, `PostToolUse`, `Stop` 순서와 동시성
- 한 차례 Stop continuation
- 역순·중복 사건의 결정적 처리
- 원문·비밀값 비저장
- Hook 실패 시 Codex 본 작업 지속과 명시적 누락 상태

과거 `FAIL-BLOCKED` 또는 `LIMITED`를 새 결과로 덮어쓰지 않고 새 실행 manifest와 판정을 만듭니다.

### 단계 3. 최소 자동 연결 구현

기존 spool·collector·DB·웹은 재사용하고, 자동 관찰에 필요한 최소 Hook adapter와 누락 검증만 구현합니다. 기존 기반을 불필요하게 재작성하지 않습니다.

### 단계 4. 실제 종단 간 수락 시험

아래 필수 시나리오를 실제 Codex 작업과 로컬 대시보드에서 확인합니다.

1. 새 Codex 작업을 만들고 대시보드 관련 지시를 하지 않아도 새 활동이 생성됩니다.
2. 파일 변경 작업이 자동으로 티켓과 Task에 연결됩니다.
3. 설명·상태 질문도 정책에 따라 `DISCUSSION_LOG` 또는 명시적 미분류 활동으로 사라지지 않습니다.
4. 기존 작업을 재개하면 과거 기록을 중복하지 않고 새 활동이 같은 식별 관계로 추가됩니다.
5. 사용자 답변 대기와 차단 상태가 실제 행동과 일치합니다.
6. 최종 응답 전에 Task·Git·Wiki·summary·status 기록이 완성됩니다.
7. 누락이 발생하면 Stop에서 최대 한 차례 보정되고, 해결되지 않으면 명시적 불완전 상태가 남습니다.
8. 웹·수집기가 꺼진 동안 사건이 spool에 보존되고 재시작 뒤 중복 없이 투영됩니다.
9. Codex와 PC 재시작 뒤 기존 DB가 유지되고 새 활동 연결이 계속됩니다.
10. 사용자의 명시적 수락 전에는 `COMPLETED`가 되지 않습니다.
11. 사용자 prompt·assistant message·transcript·Hook 출력의 원문 또는 발췌와 비밀값이 spool·DB·archive·로그·웹에 없습니다.
12. 웹의 변경 요청과 Codex 역제어 경로가 계속 거부됩니다.

### 단계 5. 완료 판정

구성요소 시험, 합성 시험과 실제 종단 간 수락 시험이 모두 통과한 뒤에도 먼저 `AUTO-PROJECTION-CANDIDATE-IN_REVIEW`로 보고합니다. 사용자가 검증 범위와 실제 화면을 명시적으로 수락한 뒤에만 제품 수준 완료를 판단합니다.
